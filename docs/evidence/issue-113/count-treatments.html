Issue #113 · decision record

Groups, Pieces, Proposals

The Armor duplicates view counts three different things and never says which is which. Two treatments, compared against rendered evidence.

The tile row mixes nouns. PROPOSED, AFTER VETOES, REVIEWED and UNREVIEWED count items. SHOWN counts groups — but only on this surface. The label and its visual weight never change; only a small sub-caption does.

The Showing N of M denominator is already filtered. M is the count after the kind selector, so both numbers move together and the string can never reveal that groups of another kind exist. The ticket's Showing 2 of 74 groups actually means “2 of the 74 groups of the currently selected kind”.

02 — The fork

Where should scope live?

Both treatments fix the noun collision. They differ on one real axis: whether the reader learns scope from one authoritative place, or from every number carrying its own. That choice drives everything else.

Alternative A

One scoped summary line

Delete the SHOWN tile from this surface. Replace it and the hint with a single accented line directly above the list that always states both nouns, both denominators, and the active filter. Group headers carry only local facts plus a piece count.

Why it works. One place answers every counting question, and it is the last thing read before the list. Both denominators are unfiltered totals, so the reader always knows what they are not seeing. The tile row becomes homogeneous — every remaining tile counts proposals.

What it costs. Scroll past the line and scope is gone; on a long list the reader re-scrolls to check. It also puts four numbers in one sentence, which wraps to three lines at 390px — measured at 61px tall, and the cheaper of the two narrow costs.

Alternative B

Every count carries its own noun

Keep counts distributed, but make each one self-describing. The tile row gains a pieces tile and splits SHOWN into its two nouns. Filter chips state what they filter. Each group header leads with a prominent piece count.

Why it works. Scope is local, so it survives scrolling — the piece count sits on the group you are actually reading. The chips answer “how many of each kind” without clicking through. Nothing needs re-reading after a scroll. Note the narrow cost, measured below: the tile row stacks rather than overflowing, but stacking is not free — it takes 178px before any group is reached.

What it costs. Count information is spread across tiles, filter chips and group headers, and they must agree: 12 appears in both the Groups tile and the Exact chip, 74 in both the tile and the All kinds chip. Each pair is a drift risk. Nothing answers “how big is this review” in one glance, and the tile row mixes four different nouns — groups, pieces, proposals, reviewed — at equal weight, which is a milder version of the problem being fixed.

Alternatives A + B · shared

Unfiltered, both kinds

The kind hierarchy is the same under either treatment, so it is shown once, in the state where both kinds actually appear. Note the scope line drops "of" when nothing is filtered, and the banner's second sentence is present only because these members carry proposals.

Measured

Both treatments at 390px

The narrow comparison below is measured on these specimens, not reasoned about. Each is constrained to exactly 390px — the width the browser checklist verifies at — and the figures in the comparison table come from rendering them.

04 — Recommendation

Take B's group cues and A's summary line

A hybrid, weighted toward B

The comparison splits cleanly: A wins on stating scope once and correctly, B wins on keeping it available while scrolling. They are not mutually exclusive, and the costs are not symmetric — A's weakness is a scroll away, B's weakness is pairs of numbers that must agree forever.

One correction from measuring. This page originally scored the 390px row as a win for B, on the reasoning that tiles and chips stack. Measured, neither treatment overflows and A is the more compact — 235px against B's 358px, because stacking B's tile row costs 178px. That does not change the recommendation; it strengthens it, since the hybrid keeps A's line and specifically declines B's expanded tile row.

So: adopt A's single scoped line as the one authoritative statement, and B's per-group piece count and review-only banner as local reinforcement that never restates a total. The tile row keeps only proposal-shaped counts, and SHOWN leaves this surface entirely.

Exact copy changes

  1. Delete the SHOWN tile on the duplicates surface, and delete "Showing " + filteredGroups.length + " of " + selectedArmorGroups.length + " groups".
  2. Add, above the list, in one aria-live="polite" region:
    12 of 74 groups · 38 of 211 pieces — filtered to exact duplicates
    Unfiltered, the same region reads 74 groups · 211 pieces with no “of”.
  3. Group header gains a piece count as its first element: 3 pieces — the noun is pieces everywhere; copies, items and members are retired from user-facing text.
  4. Kind label becomes Exact / Same stats · review only. The current "Exact duplicate group · " + group.groupKind — which renders Exact duplicate group · exact_duplicate — goes away.
  5. Same-stat banner replaces the bare sub-line, in two parts. Unconditional, because it is always true of a same-stat group:
    Base stats match but tuning differs, so this pass selects no survivor.
    Appended only when at least one member carries a proposal:
    Pieces below that already carry a proposal keep their verdict controls.
  6. Facet options state their noun when it is not groups: Melee (1 group), so the tuning facet's member-derived count stops reading as a group count.

Adopted separately: transpose the comparison table

At 390px the current member-as-column table shows exactly one member; comparing requires scrolling inside the table. A comparison view that shows one thing at a time has lost its purpose. Members become rows. This is orthogonal to the count treatment and is the single largest piece of #119 — it must carry over the existing conditional-column behaviour, where Seasonal Mod, Holofoil and Tuning Stat appear only when members actually differ.

05 — Boundaries and open questions

What this does not decide

  • Out of scope, already split: per-group bulk verdicts (#115), an armor score column (#116), the DIM query builder (#117). None is presupposed by either treatment.
  • Baseline defects (#118) are fixed independently. Two were found only by rendering: the group <h3> has no overflow-wrap, so a 180-character item name gives the page a 2266px scroll width at a 390px viewport; and the report fingerprint does the same at 549px.
  • Open — does the piece count include the survivor? “3 pieces” on an exact group counts the survivor plus two candidates. A reviewer scanning for work to do may read it as three deletions. Consider 3 pieces · 2 proposed, at the cost of a fourth number.
  • Open — what is a “piece” in a filtered view? Both figures count group members and are measured identically today, so the ratio is sound: 211 is the members of all 74 groups, 38 the members of the 12 shown, and pieces in no duplicate group are counted by neither. But the kind filter selects whole groups, so a future member-level filter would select members — at which point the two stop agreeing.
  • Open — should the summary line pin to the top on scroll? It would erase A's only real weakness, at the cost of vertical space already scarce at 390px.
  • Preserve one thing the old line did well: the empty state renders Showing 0 of 2 groups, the single case where the already-filtered denominator is genuinely informative. The replacement must keep that. The empty message also names no filter and offers no way to widen.
  • Not verified: both treatments are specimens, not the running app. Contrast, focus order and live-region announcement need checking against the real build during #119.
